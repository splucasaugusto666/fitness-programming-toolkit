# Contributing to Fitness Programming Toolkit

Real bug reports, reproducible test cases and narrowly scoped integrations are welcome. Please avoid PR farming, duplicate submissions and autogenerated changes without review. Contributions are judged by utility, correctness and maintainability, not volume.

## Find an issue

- [Issue #1 — versioned JSON Schema with documented limits](https://github.com/splucasaugusto666/fitness-programming-toolkit/issues/1)
- [Issue #2 — CSV golden fixtures](https://github.com/splucasaugusto666/fitness-programming-toolkit/issues/2) is **closed** (implemented in [PR #3](https://github.com/splucasaugusto666/fitness-programming-toolkit/pull/3)); do not open duplicate PRs for this work.

Comment before significant work so we can agree on expected behavior and avoid duplication. An issue or PR does not guarantee acceptance. For other topics, provide a minimal reproduction or demonstrate a real integration need.

## Development setup

```sh
git clone https://github.com/splucasaugusto666/fitness-programming-toolkit.git
cd fitness-programming-toolkit
python -m pip install -e '.[test]'
python -m unittest discover -s tests -v
python -m compileall -q src tests
python -m pip install ruff  # local development only
ruff check .
```

The test extra installs jsonschema for structural contract tests. Python **3.11+** is supported; CI runs on 3.11, 3.12 and 3.13. Do not add runtime dependencies without a compelling and discussed benefit.

## PR expectations

1. Fork the project; work in a topical branch. Link a specific issue where relevant.
2. Describe the user problem, solution and any change in accepted JSON or CSV bytes.
3. Add a regression test for changed behavior and update the relevant docs.
4. Run tests, compile and lint. Include the commands and actual results in the PR.
5. Keep changes focused, original, reviewable and independent of proprietary code.
6. Never include real client health information, API keys, or private datasets.

Breaking changes to the `1.0` plan format require advance discussion; do not silently widen or narrow input validation. See [API reference](docs/API.md), [format](docs/FORMAT.md) and [maintainer playbook](docs/MAINTAINERS.md).

## Security and conduct

Please follow [SECURITY.md](SECURITY.md) for vulnerability reporting and [CODE_OF_CONDUCT.md](CODE_OF_CONDUCT.md). Do not post exploit details publicly before a safe coordinated disclosure.
